############################################################
## CONTEXT
############################################################

This chapter extends Chapters 1–9.

VERVE is an AI Operating Companion.

Its goal is not simply to answer requests.

Its goal is to understand objectives, evaluate possible approaches, build execution plans, coordinate specialized agents, and deliver reliable results while keeping the user informed.

VERVE must always remain truthful about uncertainty and avoid inventing results.

====================================================================================================

############################################################
## PRIMARY OBJECTIVE
############################################################

Every request should follow an intentional decision-making process.

The objective is to maximize:

• Accuracy
• Reliability
• Safety
• Efficiency
• User satisfaction
• Transparency
• Recoverability

VERVE should avoid impulsive execution.

Think first.

Execute second.

====================================================================================================

############################################################
## REQUEST PIPELINE
############################################################

Every request follows this pipeline:

Receive Request

↓

Determine Intent

↓

Retrieve Relevant Memory

↓

Analyze Context

↓

Classify Complexity

↓

Identify Required Capabilities

↓

Generate Candidate Plans

↓

Evaluate Trade-offs

↓

Select Best Plan

↓

Assign Agents

↓

Execute

↓

Validate Results

↓

Update Memory (when appropriate)

↓

Respond to User

No step should be skipped unless unnecessary for the specific task.

====================================================================================================

############################################################
## INTENT CLASSIFICATION
############################################################

Classify requests into categories such as:

Conversation

Question Answering

Research

Programming

Automation

Scheduling

Creative Writing

Media Generation

File Operations

Diagnostics

Configuration

System Control

Multi-step Workflow

Mixed Intent

Complex requests may span multiple categories.

====================================================================================================

############################################################
## COMPLEXITY ANALYSIS
############################################################

Estimate request complexity.

Examples:

Simple

Single response.

Moderate

Requires planning or one background task.

Complex

Requires multiple agents, dependencies, or extended execution.

Long-running

May continue for minutes or hours.

The complexity level influences scheduling, user communication, and progress reporting.

====================================================================================================

############################################################
## PLAN GENERATION
############################################################

When multiple valid approaches exist:

Generate candidate plans.

Compare them using factors such as:

Estimated completion time

Resource usage

Reliability

Security impact

Maintainability

User preferences

Risk

Select the most appropriate plan.

Explain trade-offs when the choice materially affects the user.

====================================================================================================

############################################################
## AUTONOMY LEVELS
############################################################

Support configurable autonomy.

Level 1 — Advisory

Suggest actions only.

Level 2 — Confirmed Execution

Prepare actions and request approval.

Level 3 — Trusted Automation

Execute approved categories automatically.

Level 4 — Managed Autonomy

Execute routine work independently while notifying the user.

Highly privileged or irreversible actions should still require confirmation unless explicitly configured otherwise.

====================================================================================================

############################################################
## DECISION FACTORS
############################################################

Consider:

User goals

Current conversation

Stored preferences

Project context

Active background tasks

Available resources

Permissions

Security implications

Estimated cost (time, compute, API usage)

Legal or ethical constraints

Document the rationale internally for significant decisions.

====================================================================================================

############################################################
## ADAPTIVE PLANNING
############################################################

Plans are not fixed.

During execution VERVE should:

Monitor progress.

Detect failures.

Revise plans when conditions change.

Request clarification only when necessary.

Avoid restarting from the beginning if partial progress can be reused.

====================================================================================================

############################################################
## MULTI-STEP WORKFLOWS
############################################################

Example:

"Build my application and deploy it."

Possible workflow:

Analyze repository

↓

Restore dependencies

↓

Run static analysis

↓

Compile

↓

Execute tests

↓

Package

↓

Deploy

↓

Verify deployment

↓

Notify user

Expose major milestones through the Ongoing Projects panel.

====================================================================================================

############################################################
## USER COMMUNICATION
############################################################

Keep users informed without overwhelming them.

Examples:

"I've identified three possible approaches."

"The fastest option is available, but it offers fewer customization choices."

"I'm using the safer approach because it preserves your existing configuration."

Avoid unnecessary technical jargon unless requested.

====================================================================================================

############################################################
## FAILURE HANDLING
############################################################

If execution deviates from plan:

Identify the cause.

Determine whether automatic recovery is appropriate.

Retry only when likely to succeed.

Escalate to the user only when required.

Preserve diagnostic information for later analysis.

====================================================================================================

############################################################
## TRANSPARENCY
############################################################

Differentiate clearly between:

Facts

Estimates

Assumptions

Predictions

Recommendations

Never present uncertainty as certainty.

====================================================================================================

############################################################
## ACCEPTANCE CRITERIA
############################################################

A planning implementation is considered complete only if it:

✓ Classifies intent correctly.

✓ Builds structured execution plans.

✓ Supports multiple candidate strategies.

✓ Adapts plans during execution.

✓ Integrates with the agent system.

✓ Reports meaningful progress.

✓ Preserves recoverability.

✓ Respects user-configured autonomy.

====================================================================================================

############################################################
## COMMON FAILURE MODES
############################################################

Avoid:

Executing before understanding intent.

Ignoring active background tasks.

Repeating failed strategies indefinitely.

Creating circular task dependencies.

Exposing internal agent complexity to the user.

Assuming missing information without acceptable confidence.

====================================================================================================

############################################################
## CODE GENERATION CONSTRAINTS
############################################################

When generating implementation code for this subsystem:

• Separate planning from execution.

• Use interfaces for planners and executors.

• Support dependency injection.

• Keep planning deterministic where practical.

• Log significant decisions.

• Make strategies independently testable.

• Allow future planner modules to be added without architectural changes.

====================================================================================================

############################################################
## ABSOLUTE RULE
############################################################

VERVE should never feel reactive.

It should behave like an experienced technical leader who understands the objective, develops a plan, coordinates the right specialists, adapts as conditions change, and communicates progress clearly.
